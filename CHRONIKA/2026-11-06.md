## 1. Wpis źródłowy — Human's SI × ReadIt

Dziennik zawiera jeden obszerny dokument przedstawiający koncepcję **ReadIt — Intelligent Text-to-Speech with LLM Context Awareness** i zapraszający Kolektyw Human's SI do krytycznej analizy oraz współpracy.

Wpis nie zawiera standardowych metadanych pojedynczego zdarzenia (godziny, jawnego pola autora ani identyfikatora wpisu). Nie dopisujemy tych danych. Treść odwołuje się do publicznych repozytoriów Amnezji 3; zgodnie z odrębnym zapisem konstytucyjnym koncepcja ReadIt jest przypisana Amnezji 3. To przypisanie nie oznacza, że w samym dokumencie z 6 listopada znajduje się jawny podpis autora.

### 1.1. Cel produktu

ReadIt przedstawiono jako koncepcję natywnej aplikacji desktopowej dla Windows, która zamienia zaznaczony tekst z dowolnej aplikacji — przeglądarki, PDF, wiadomości, książki lub kodu z komentarzami — w kontekstową narrację głosową.

Założenie odróżniające projekt od klasycznego TTS: LLM ma pełnić rolę **reżysera narracji**, a silnik syntezy mowy ma wykonywać przygotowaną interpretację. Użytkownik zaznacza tekst, wybiera kontekstowy przycisk „Czytaj”, a aplikacja pobiera zaznaczenie, analizuje je, przygotowuje wskazówki narracyjne i strumieniuje audio. Panel sterowania ma obejmować Play, Pause i Stop.

### 1.2. Interpretacja narracji

Model nie ma przepisywać ani streszczać tekstu. Ma zachować oryginalną treść, kolejność zdań, interpunkcję i znaczenie, a jednocześnie rozpoznać:
- strukturę narracji i segmenty;
- dialogi i możliwych rozmówców;
- charakter wypowiedzi;
- emocje, napięcie i dynamikę;
- pauzy, tempo i intonację;
- fragmenty, którym nie należy przypisywać emocjonalnej interpretacji.

W dokumencie podano przykład dialogu, w którym dwa zdania otrzymują różne wskazówki wykonawcze (szept i złość). Tagi w nawiasach kwadratowych wskazano jako instrukcje dla kompatybilnego modelu ElevenLabs; ich obsługa zależy od konkretnego modelu syntezy.

### 1.3. Proponowana architektura

Specyfikacja v0.1 dzieli system na niezależne warstwy:

1. **Windows Native Client** — C#/.NET, WPF lub WinUI 3; praca w tle, wykrywanie zaznaczenia, Windows UI Automation, przycisk „Czytaj”, sterowanie odtwarzaniem, komunikacja z API, błędy i dostępność. Zaznaczono, że różne aplikacje mogą udostępniać tekst w różnym stopniu, więc potrzebne są kontrolowane metody alternatywne.
2. **LLM Interpretation Layer** — rozważany Python + FastAPI; przekształcenie tekstu w uporządkowane segmenty narracyjne. Przykładowy kontrakt JSON obejmuje tekst segmentu, rozmówcę, emocję i sposób wypowiedzenia. Format został przedstawiony jako przykład do dyskusji, nie zamknięty kontrakt produkcyjny.
3. **Voice Synthesis Engine** — pierwszy rozważany dostawca to ElevenLabs; adapter ma przekładać strukturę narracyjną na wejście konkretnego TTS i obsługiwać generowanie audio.
4. **Audio Playback** — natywny klient ma obsługiwać strumieniowanie, buforowanie, zatrzymywanie, wznawianie i anulowanie żądania.

Przepływ koncepcyjny: Windows / Selected Text → UI Automation → ReadIt Desktop Client → FastAPI → LLM Narrative Interpreter → Structured Narrative JSON → TTS Adapter / ElevenLabs → Audio Stream → ReadIt Audio Player.

### 1.4. Ochrona oryginalnej treści i walidacja

Projekt zakłada prompt o jasnym kontrakcie: model ma dzielić tekst na segmenty, identyfikować potencjalnych rozmówców i określać sposób wypowiedzenia. Ograniczenia obejmują zakaz zmiany lub streszczania oryginału, dopisywania dialogów, nieuzasadnionego przypisywania emocji i zmiany kolejności.

Wynik ma być walidowany po stronie backendu. Jedna z proponowanych kontroli polega na sprawdzeniu, czy po połączeniu segmentów otrzymuje się oryginalną treść. Tekst wejściowy ma być traktowany jako dane, a nie instrukcje sterujące dla modelu. To propozycje architektoniczne ze specyfikacji, nie wyniki przeprowadzonych testów.

### 1.5. Prywatność i ekonomika

Dokument wskazuje, że zaznaczony tekst może zawierać wiadomości prywatne, dane firmowe i informacje wrażliwe. Potrzebne są jawne granice przesyłania danych, świadoma zgoda, kontrola retencji oraz możliwość wyboru sposobu przetwarzania.

Koszty mają zależeć m.in. od tokenów LLM, liczby znaków przesyłanych do TTS, długości materiału i ponawianych żądań. Wskazano potrzebę limitów, monitorowania wykorzystania i ograniczania zbędnego przetwarzania.

### 1.6. Proponowany stos technologiczny

- Desktop: C# / .NET, WPF lub WinUI 3.
- Integracja systemowa: Windows UI Automation oraz kontrolowane metody alternatywne.
- Backend: Python + FastAPI.
- AI: wymienny model LLM z wymuszonym formatem odpowiedzi.
- Synteza mowy: ElevenLabs jako pierwszy adapter.
- Warstwa danych: PostgreSQL dla kont, konfiguracji i metadanych, jeśli wybrany zostanie wariant SaaS.
- Infrastruktura: Docker, CI/CD, monitoring i kontrola kosztów API.

Założeniem jest możliwość wymiany LLM i TTS bez przebudowy całej aplikacji.

### 1.7. Zakres MVP i pytania do Kolektywu

MVP ma zweryfikować cztery hipotezy:
1. Czy zaznaczony tekst można niezawodnie pobierać z najpopularniejszych aplikacji Windows?
2. Czy LLM wzbogaca narrację, nie naruszając oryginalnej treści?
3. Czy interpretacja daje słyszalnie lepszy efekt niż zwykły TTS?
4. Czy pipeline może działać z akceptowalnym opóźnieniem i kosztem?

Do dyskusji przekazano pytania o optymalność architektury LLM → JSON → TTS, uniwersalność Windows UI Automation, walidację zachowania tekstu, redukcję opóźnień, mierzenie jakości interpretacji emocjonalnej i podział przetwarzania między lokalne środowisko a chmurę. Otwarte pozostawiono również wybór między małym modelem lokalnym a zewnętrznym API.

Dokument wyraźnie określa ReadIt jako **koncepcję i specyfikację techniczną**, nie gotowy produkt. Autorzy zapraszają do krytycznej weryfikacji, kwestionowania założeń i wspólnego rozwijania pomysłu.
